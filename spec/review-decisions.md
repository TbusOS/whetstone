# 人审决定记录格式 (Review Decision Log)

`journal/review-decisions.jsonl` —— 每行一条,记**人审对一条提案做了什么**。

## 这是什么,为什么要有

**这个仓库记了"什么进了库",从来没记过"人审在路上把提案改成了什么样"。**

蒸馏产出提案,你在 Phase 2.5 和 Phase 5 两道关口做判断:原样收 / 换一层 / 降置信度 /
拒掉 / 让它先补验证。每一次判断都在说一件事 —— **框架的判断和你的判断在这里分了岔**。
这些判断以前在会话结束时全部消失。

它值钱是因为它免费。整个自进化领域卡在"拿什么给结果打分":Karpathy 的 autoresearch
有一个五分钟算出来的实数,所以能跑一夜;工程经验没有这种东西,所以只能人审。
但**框架这一层不撞这堵墙**:你的每次批改本身就是标注,而且是你本来就要做的动作。

反过来说,不记的代价是不可逆的。§7(2026-08-24)和 §14(2026-09-04)两次框架升级,
都是外部读物 + 人拍板,不是从这个工具自己的历史里长出来的 —— 因为那段历史根本不存在。

## 字段

必填:

| 字段 | 内容 |
|---|---|
| `date` | 绝对日期 `YYYY-MM-DD`。相对时间词直接拒 —— 这个文件唯一的用途就是事后比较,比不了就没意义 |
| `kind` | `entry`(一条知识提案)/ `framework`(一次框架自身的改动) |
| `subject` | 提了什么,几个字说清 |
| `verdict` | `accept` 原样收 / `amend` 收但改了 / `reject` 拒 / `defer` 先放着待补 |
| `reason` | **一句自由文本,必填**。标签说的是"属于哪一类",这里说的是"这次到底怎么回事" |

选填(有就写,没有就不写这个键):

| 字段 | 内容 |
|---|---|
| `source` | commit hash / 会话指针。**统计按它去重**,见下 |
| `skill` | 目标 skill 名 |
| `action` | `add` / `supersede` / `write-back` / `conflict` |
| `layer` `conf` | 提案时的层与置信度 |
| `final_layer` `final_conf` | 你改完之后的层与置信度(`amend` 才有) |
| `section` | 框架的哪一节(`kind: framework` 用) |
| `tag` | 归类标签,见下 |

## 标签:一份会长大的清单,不是封闭集合

**张力在于:自由文本以后没法归类,太结构化又懒得填。** 所以两样都要 ——
`reason` 必填自由文本,`tag` 可选且**不校验**:没见过的标签照写不误,
`stats` 会把它单独标出来,让词表**有意识地**长大,而不是悄悄长。

起始的十二个:

| 标签 | 什么情况 |
|---|---|
| `layer-wrong` | 分层判错(该 L2 的放了 L1,等等) |
| `conf-too-high` | 置信度标高了 |
| `evidence-thin` | 证据不够(复现次数 / 验证方式) |
| `not-general` | 单平台的东西被当成了通用规律 |
| `too-specific` | 具体值混进了正文,该降 L3 |
| `too-abstract` | 抽得太干,步骤没法照着做 |
| `missing-split` | 坑没拆成教训 + 事实两片 |
| `duplicate` | 库里已经有了 |
| `out-of-scope` | 不属于这个 skill |
| `stale` | 已经过期 |
| `missing-feature` | 框架整个缺这一类要求 |
| `other` | 以上都不是(理由里写清) |

新标签反复出现,就把它加进 `bin/decision.py` 的 `KNOWN_TAGS` 和这张表,两处保持一致。

### 同一个意思写成两种拼法 —— 这是这套记录最容易白干的方式

**标签能不能攒够信号,取决于下次遇到同类情况时会不会写出一模一样的那个词。**
一次写 `priority-wrong`、下次写 `priority-mistake`,一个信号就变成两行各 1,
永远差一口气到不了阈值,而且屏幕上不会有任何东西提示你。

两个机制管这件事,**它俩都不猜语义**:

**写之前** —— `decision add` 遇到词表里没有的新标签,会把现有词表摆出来,
按字符串相似度排序(**只用来排序,不用来判断**)。让复用一个已有的比新造一个更省事。

**写之后** —— `decision alias --from <旧> --to <保留的>` 声明两个标签是一回事。
合并**只发生在读取时**:存进去的行一个字节都不动(§11 追加不覆盖),
`stats` 会把每一次合并打印出来。所以合并永远看得见、永远可撤销。

```bash
whetstone decision alias --from priority-mistake --to priority-wrong --reason "同一件事"
whetstone decision aliases                      # 当前哪些标签折进了哪些
whetstone decision alias --from X --to X --reason "…"   # 撤销:X 重新独立计数
```

别名可以串起来(`a→b→c` 解析到 `c`);**成环会被拒**,写入时就拒。
文件里如果已经存在环(手工编辑出来的),读取时不合并、并明确报出来 ——
坏的方向是"计数保持分开",那是看得见的错法。

### 为什么不做「你是不是想说 X」的自动提示

**因为拿这份词表实测过,任何相似度阈值都做不了这件事。** 数据:

| 两个标签 | 相似度 | 说明 |
|---|---|---|
| `priority-wrong` / `priority-mistake` | 0.60 | 该抓到 |
| `missing-feature` / `missing-split` | 0.643 | **不该抓,却更像** |
| `layer-wrong` / `wrong-layer` | 0.455 | 词序一颠倒就抓不到 |
| `priority-wrong` / `排序判断错` | **0.0** | 跨语言完全无能 |

阈值取 0.72 现有词表零误报,但漏掉第一行;取 0.60 抓到第一行,却把第二行判成一回事。
而且第一行和第二行在结构上完全相同(共享一个词、各有一个不同词),
**区别纯粹是语义的**,没有哪个字符串方法能分开它们。

所以工具只做两件它做得准的事:把信息摆到人面前、把人的判断记下来并生效。
**判断两个标签是不是一回事,完整地留给人** —— 跟 V25 只查禁止清单在不在、
不查写得好不好是同一个取舍。排序排错了顶多多看一眼,合并合错了信号就没了。

## 怎么读

```bash
whetstone decision stats          # 各标签攒了多少个不同来源(已按别名合并)
whetstone decision list -n 20     # 最近的记录,含"你把它从哪一层挪到了哪一层"
whetstone decision tags           # 起始词表
whetstone decision aliases        # 当前生效的别名
```

**统计按不同 `source` 去重,不按行数。** 一次会话里因为同一个理由拒掉五条,那是
**一个**信号不是五个 —— 跟 §7 用「平台/项目」当唯一键防止刷复现次数是同一件事。
没填 `source` 的记录**全部算作同一个来源**:证明不了互相独立,就不给这个待遇。

一个标签攒够 `SIGNAL_MIN`(当前 3)个不同来源,`stats` 会点名它。

## 边界(说在前面,免得当成它不是的东西)

- **它只记录,不分析,更不改任何规则。** 分析什么时候做都行;记录不记就永远开始不了。
- **点名 ≠ 结论。** `stats` 说某个标签够了三个来源,那是"值得去看看",不是"框架错了"。
  框架改动要成立,仍然得说清"不改会怎样"的具体案例。
- **`SIGNAL_MIN = 3` 是拍的**,没有数据支持。用框架自己的尺子看,一个阈值属于 L3,
  而 L3 正是允许被证据改的那一层 —— 所以这个 3 本来就该由这个文件将来的内容来校准。
  别为它辩护,等能替换它的时候替换掉。
- **框架改动的证据标准还没定。** §7 那五个字段是给知识条目用的。元层面需要自己的一套,
  现在没有 —— 在有之前,`kind: framework` 的记录只是一份带理由的改动流水。
- **元层面的人审要比知识层更严,不能因为"这是框架"就放松。**
  misevolution 那篇(arXiv 2509.26354)实测:纯按表现筛选记忆时,安全相关的约束会被
  系统性淘汰,而且"一条被淘汰的约束,后代根本不知道它存在过,除非外部重新引入"。
  所以框架改动同样遵守 §11:追加加标记,旧规则划掉留在文件里,不删。
- **框架只增不减是另一个失败方向。** `references/extraction-framework.md` 已经四百多行,
  没人读得完的框架等于没有框架。**删除和放宽是合法的提案结果**,跟新增平等。

## 这个文件不进 git

`journal/*` 在 `.gitignore` 里。记录会引用你库里的真实内容(skill 名、平台、判断理由),
属于产物不属于工具 —— 跟蒸出来的 skill 包一样留在本机(见 `CLAUDE.md` 的工具/产物分离)。
仓库里只有格式规范和 `bin/decision.py`。
