# 经验路由规范 (Experience Routing)

> 状态:2026-09-29 草稿,待 user 审。第 5 节第一期尚未实现。第 2 节的数字来自同日一台机器上的测量,
> 样本条件写在表里,菜单相关的部分可用 `whetstone lint --listing` 与 `whetstone menu-snapshot --events` 复现。

**一句话**:经验库越大,越不能指望模型从一张平铺的菜单里自己挑中该用的那条。
「这条经验此刻该不该出现」尽量交给**确定的信号**判断 —— 在哪个目录干活、读到了哪个文件;
只有纯聊话题、不碰文件时,才靠模型去查一份**自动生成的总目录**。默认不装任何钩子。

## 1. 这是什么,为什么要有

**路由 = 决定「这一刻哪条经验该进入模型视野」的机制。** 它不产生经验,也不判断经验对错
(那是蒸馏和 `use-time-conflicts.md` 的事),只管经验在该出现的时候出现。

**没有它会怎样**:runtime 把每个 skill 的名字和描述拼成一张菜单放进上下文,模型读描述决定用哪个。
这张菜单有总预算;超了 runtime 不删 skill,而是去掉一部分描述、只留名字 —— 描述里写的触发词,
模型就看不到了。预算是固定的,库是一直长的,平分到每条描述的份额只会越来越小:

| 库里的 skill 数 | 每条描述能分到(Opus 会话,留给库约 16,000 字符,每条名字和格式约 20) |
|---|---|
| 65 | 约 226 字符 |
| 100 | 约 140 |
| 200 | 约 60 |
| 300 | 约 33 —— 低于一条能被匹配的描述需要的 40 |

上下文小的模型更早撑不住:同一个库在 Haiku 4.5 会话里,留给库的只有约 1,190 字符,65 个 skill 全部只剩名字。

**为什么不是继续缩描述**:缩描述只是推迟上面那张表的结局。库要能一直长,
入口就不能跟着 skill 数一起变长 —— 只能是**固定大小的入口 + 按需读取的目录**,
或者**不经过菜单、由别的信号直接带出来**。runtime 自己也是这么处理大量工具的:
工具很多时只列名字,用到时再按名字取出完整定义。

## 2. 实测依据(2026-09-29,一台机器,Claude Code)

| 事实 | 样本 | 结果 |
|---|---|---|
| 按工作目录触发(常驻规则写明「在某目录下用某 skill」) | 30 天、10 个会话 | 8 个加载了对应 skill |
| 按描述里的触发词触发 | 30 天、38 组「会话 × skill」 | 5 组加载(13%) |
| 同上,按菜单里有没有描述拆开 | 197 条命中消息 | 有描述 26%(98 条);只剩名字 1%(99 条) |
| 菜单预算 | 76 份会话开头的菜单(Opus) | 24,536–26,880 字符,条目从 69 涨到 111,带描述的一直 46–56 条 |
| 预算跟模型走 | 同一个库,Opus 与 Haiku 4.5 各一份 | 25,123 字符 / 7,978 字符 |
| 放在 `<目录>/.claude/skills/` 的 skill | 4 个无交互测试会话 | 从该目录启动:有;从它的子目录启动:有(该目录不是 git 仓也会往上找);从别的项目启动:没有;从上层目录启动、中途读到该目录里的文件:同一秒补进菜单 |
| `disable-model-invocation: true` 的 skill | 1 个测试会话、3 个 skill | 菜单里连名字都没有 |

统计脚本与完整报告在使用者的私有库,不随本仓发布;可复现的部分是 `whetstone lint --listing`
与 `whetstone menu-snapshot --events`(见 `adapters/menu/README.md`)。
样本只来自一台机器、一个使用者,比率只描述这段时间,不能外推。

## 3. 原则

1. **确定信号优先于模型判断。** 目录、文件路径是事实;「模型读了描述觉得相关」是推断。
   上表里前者 8/10,后者 13%。
2. **只给指针,不塞正文。** 任何自动带出的东西只说「有这条经验、在哪」,
   读不读正文由模型决定。
3. **钩子最少**(user 2026-09-29 定)。默认一个都不装;要装必须先满足第 6 节的全部条件。
   **为什么**:干活时执行命令、读写文件极其频繁,挂在这些动作上的钩子几乎每一步都跑,
   哪怕每次只加一行,累计起来也影响体验;而且它坏的方式是「一直在响」,副作用大。
4. **不要求使用者记住 skill 的名字。** 不用「只许手动调用」(`disable-model-invocation`)
   来省菜单 —— 库大了使用者根本不知道有哪些 skill,标成只能点名调用等于藏起来。
   例外:本来就只由人点名用的(比如「检查 skills 更新」这种维护命令)。
5. **runtime 中立。** 总目录是纯文本,任何 runtime 都能读;依赖某个 runtime 的部分
   (目录作用域、钩子)只放在 `adapters/`,或写明「只在 X 上实测过」。

## 4. 三种触发

### ① 按在哪干活

**是什么**:只在某个项目里有用的经验,只在那个项目里出现。

**机制**(Claude Code,已实测,见第 2 节):skill 放进 `<项目目录>/.claude/skills/<名字>/`。
从该目录或它的子目录启动的会话,开局菜单里就有;从别处启动的会话,读到该目录里的文件时中途补进。
不占全局菜单,也不需要钩子。

**whetstone 做什么**:经验库的仓里放一份作用域清单 `skill-scopes.tsv`,一行一个 skill:

```
<skill 名>	<目录>[	<目录> ...]      # 路径可以用 ~
```

`deploy.sh --link` 读它:清单里的 skill 不链进全局目录,而是链进清单里写的那些目录下的 `.claude/skills/`;
不在清单里的照旧进全局。清单写的是本机路径,所以放在经验库的仓里,**不进可移植的包**。

**适合**:产品工作流、产品专属参数这类只在一个项目里成立的经验。
**不适合**:跨项目的专题经验(签名、分区、git 纪律……)—— 它们没有归属目录,走 ③。

### ② 按正在做的动作(钩子,默认不装)

**是什么**:执行某条命令、改某类文件之前,查一下目录里有没有对应的坑,有就给模型加一行指针。

**为什么有价值**:坑的价值就在动手那一刻 —— 准备烧录时看到那条烧录的坑,正好用得上;
也和用时冲突同一个思路,模型刚被提醒过,更容易发现经验和现场对不上。

**为什么默认不装**:见原则 3。它是三种里最频繁的,只有第 6 节的数字证明它足够安静时才考虑。

### ③ 按聊的话题

**是什么**:一个自动生成的「路由 skill」(默认名 `experience-router`),正文是整个库的分族目录。
模型不确定有没有相关经验时先查它,查到名字再去用那条经验。

**生成**:`whetstone index --router` 从库里每个 skill 的名字和描述生成,不手工写:

- 入口描述 ≤ 200 字符,只说一件事:「做专业领域的任务、不确定有没有相关经验时,先查这里」。
- 正文按族分组,每个 skill 一行:名字 · 一句话能力 · 触发词 · 作用域。
- 作用域限定的 skill 标出它的目录和 `SKILL.md` 路径:在那个目录外要用,先读这个文件。
- 目录超过 150 条或 20,000 字符时拆成两层:总目录只列族,每族一份分目录。数字暂定,按实测调。

**双保险**:常驻的全局规则文件(Claude Code 是 `CLAUDE.md`)里写同样一句话和目录的路径。
**为什么**:新生成的路由 skill 没有调用记录,菜单超预算时 runtime 会先去掉最少用的 skill 的描述 ——
它恰恰最容易先被去掉;常驻规则那一句不受菜单预算影响。

**查到之后怎么用**:只剩名字的 skill 照样能按名字调用,优先用调用(压缩对话后 runtime 会重放已调用的
skill);作用域外的 skill 用读文件的方式读它的 `SKILL.md`。

**规模**:目录一行一个 skill,[推断]一行约 100–150 字符(按现有描述第一句话的长度推的,生成后以实际为准),
只在查的时候进上下文;菜单里常驻的只有入口那一条。

## 5. 分期

**第一期:不装任何钩子**

1. `deploy.sh --link` 支持 `skill-scopes.tsv`(自检覆盖:清单里的不进全局、进清单写的目录;
   清单外的照旧;清单里写错的目录要报错,不能跳过了不吭声)。
2. `index.py --router` 生成路由 skill;`lint` 检查路由目录是不是最新
   (库里有而目录里没有的 skill → 警告)。
3. 使用者的私有库:定首批 `skill-scopes.tsv`(哪些进哪个目录由 user 定)、生成路由 skill、
   常驻规则里加那一句。
4. 验收:新会话里 `whetstone menu-snapshot --events` 看得到路由 skill 带着描述;
   跑第 7 节的指标。

**第二期:只读历史,不装任何东西**

用使用者 30 天的会话记录离线回放 ② 和「按消息匹配」的钩子:每个会话会提示几次、
提示了多少条后来真被用上的经验、能补回第 2 节里几个漏掉的例子。

**第三期:需要 user 同意**

第二期的数字满足第 6 节,且 user 同意,才装;一次只装一个。

## 6. 钩子准入条件(全部满足才能提议装)

1. **离线回放的数字**:每个会话提示次数中位数 ≤ 1,90 分位 ≤ 3(暂定,user 可改);
   并写明能补回哪几个漏掉的例子。
2. **提示只给模型看**,不在使用者屏幕上刷出来 —— 装之前先在真实会话里确认这一点
   (2026-09-15 撤掉旧钩子,就是因为写给模型的提示整段打到了使用者屏幕上)。
3. **同一条经验每个会话最多提示一次,每轮最多一条。**
4. **不拦任何操作**,只提示。
5. **一个开关整个关掉**(环境变量),关掉后行为必须和没装时相同。
6. **装上一周后重测**:提示过的经验真被模型用上的比例太低,就撤。

## 7. 验收怎么量

| 指标 | 现在 | 方向 |
|---|---|---|
| 按话题触发:触发词出现的会话里加载了该 skill 的比例 | 13%(5/38) | 上升 |
| 按目录触发 | 8/10 | 不下降 |
| 菜单里只剩名字的 skill 数(`lint --listing`) | 35/65 | 下降 |
| 路由 skill 被调用的次数(`menu-snapshot --events`) | 0(还没有) | 有调用,且调用后接着用了查到的 skill |

同一套统计脚本重跑,样本条件写清(几个会话、哪段时间、哪台机器)。

## 8. 禁止清单

1. 不用 `disable-model-invocation` 来省菜单空间(原则 4 的例外除外)。
2. 不装没经过第二期离线回放的钩子。
3. 钩子和路由都不往上下文里塞经验正文,只给指针。
4. 路由目录不手工改 —— 只由生成器写,改了会在下次生成时被覆盖。
5. 机器相关的路径不进可移植的包(作用域清单留在经验库的仓里)。

## 9. 边界

- ③ 仍然依赖模型想起去查路由。① 和常驻规则那一句减轻它,不能保证;
  这正是 ② 存在的理由,也是它准入条件那么严的原因。
- 目录作用域和 `disable-model-invocation` 的行为只在 Claude Code 上测过(第 2 节后两行,共 5 个测试会话);
  别的 runtime 要各自测,测不了就只用 ③。
- 菜单预算随模型变。上下文小的模型上菜单几乎全是名字,路由 skill 是唯一可靠的入口。
- 不解决经验内容本身对不对 —— 那是 `use-time-conflicts.md`。
- 路由只能带出库里有的经验;库里没有的,是蒸馏的事。
