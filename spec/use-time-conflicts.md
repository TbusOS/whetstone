# 用时冲突处理规范 (Use-time Conflict Protocol)

> 状态:2026-09-28。第 7 节的两步记录、第 8-9 节的打分与确认分档已在 `bin/decision.py` 实现
> (`whetstone decision report` / `resolve` / `miss` / `exam` / `stats`);
> 第 8 节 ② 的考卷题目本身还没出,出题要从真实经验改写。

**一句话**:agent 在干活时用到库里的经验,发现它和当前代码 / 实测对不上,
要先分类、按证据说话、主动报给人;要改经验,先说清哪里不对、改成什么、为什么,
人确认了才改。每次冲突 AI 和人各自怎么判都记下来,用来给 AI 的判断打分。

## 1. 这是什么,为什么要有

**这是经验入库之后的纠错通道。** 蒸馏(`SKILL.md` Phase 0-5)管的是"新经验怎么进库";
这份规范管的是"库里的旧经验在被使用时发现不对,怎么改"。

**没有它会怎样**:经验只在入库那一刻被审一次,之后没人再核。代码改了、平台换了,
经验照旧顶着原来的置信度被调用。更常见的是另一种坏法:agent 发现经验对不上,
自己绕过去把活干完,一个字不提 —— 经验没被改,下次照样误导,而且没有任何迹象。

**为什么在"用的时候"而不是"入库的时候"判对错**:入库时手里只有会话记录和文本,
判断对错没有依据(SkillLens,arXiv 2605.23899:无引导的 LLM 裁判在两个 skill 里挑更好的,
准确率 46.4%)。用的时候不一样:当前代码、git 历史、板子就在眼前,
**说法对不对可以直接查**。已有工作走的是同一条路:

- GLOVE(arXiv 2601.19249):观察与记忆不符时,先重做再改记忆
- arXiv 2505.16067:"future task evaluations can serve as free quality labels for stored memory"
- SEMV:核实过的矛盾存为反证,不直接替换旧规则;负迁移 5.7% → 0.2%(出处:arXiv 2609.27175 Tab.8)

**反过来的教训**:让 LLM 自己判完直接改,是记忆系统里最常见的坏法。
mem0 在 v2.0.0(2026-04)把 LLM 的 UPDATE / DELETE 整个去掉,只新增、矛盾只做关联;
Graphiti 的 issue #1728:"Nothing checks the LLM's contradiction call"。
所以本规范里 **AI 只负责发现、分类、提建议,改不改永远由人定**。

## 2. 什么时候算冲突

下面任何一种出现,都要走本规范,不能自己消化掉:

| 触发 | 例子 |
|---|---|
| 照经验做的一步失败了 | 经验给的命令报错、文件不存在、读回的值跟经验记的不一样 |
| 动手前核对,说法对不上 | 经验说"X 在这个分支上没生效",当前代码里 X 已经被调用 |
| 人纠正了一步,而那一步是照经验做的 | 人说"不对,应该是 Y",而 Y 和经验矛盾 |
| 两条经验对同一件事说法不同 | 两个 skill 给了不同的做法 |
| **我没照经验做** | 我判断经验不对,换了个做法 —— 这本身就是冲突,必须报 |

最后一行最容易漏。**偏离了已加载经验的任何一步,都要说出来。**

**不算冲突的**:新情况只是补充了一个经验没覆盖的场景,和经验不矛盾。
这走正常蒸馏(新条目或平台变体),不走本规范。未经训练的记忆管理器常把"补充"
当成"矛盾",删掉旧的再加新的,把记忆打碎(Memory-R1,arXiv 2508.19828 Fig.1)。

## 3. 先分类:冲突不等于经验错

**代码和经验对不上,至少有五种原因,只有一种是经验本身错了。**

### 两点核对法

把经验的说法**在它的来源 commit 上核一次,在当前代码上再核一次**。
经验本来就带"来源"字段(§7),这一步只读、可重复:

```bash
git grep -n '<关键串>' <来源commit> -- <路径>       # 来源处成立吗
git grep -n '<关键串>' HEAD -- <路径>               # 现在成立吗
git log --oneline <来源commit>..HEAD -- <路径>       # 中间谁改过
git log -S '<关键串>' --oneline -- <路径>            # 这个串是哪笔加 / 删的
```

`git grep` 0 命中先查写法有没有覆盖全(宏拼接、换行、大小写),再下"不成立"。
板上状态、硬件值这类不在代码里的经验,两点 = 经验里记的那次原始读数 vs 现在重读一次。

### 判定表

| 来源处 | 现在 | 经验是哪类 | 判为 | 处理 |
|---|---|---|---|---|
| 成立 | 不成立,中间有相关提交 | 事实 / 做法 | `stale` 过期 | 更新,旧值留作历史;补上"在哪个版本之前成立" |
| 成立 | 不成立,中间有相关提交 | 坑 / 禁止,且现在的写法正是它警告的那种 | `code-regress` 代码又犯了 | **不改经验**,报代码问题;这次算经验被印证 |
| 成立 | 成立 | 当前平台 / 分支与经验记的不同,现象不符 | `scope` 范围不符 | 加平台变体(§6),不动通用规律 |
| 不成立 | — | — | `wrong` 原本就错 | 替代;"当初为什么判错"本身记成一条教训 |
| 两条经验 | | | `clash` 经验互相矛盾 | 两条都摆出来,人定 |
| 成立 | 不成立,中间**没有**相关提交 | — | 核不清 | 说法依赖代码之外的东西(配置、硬件),证据档降级 |
| 没有来源 commit,或拿不到 | | | 核不清 | 同上 |

**为什么 `code-regress` 要单列**:坑之所以成为坑,往往正是因为按直觉、按文档、
按原理推出来的做法是错的。用第一性原理去"纠正"一条坑,等于把坑重新挖开。
misevolution 测过这个方向(出处:arXiv 2509.26354):只按表现筛选时,
安全相关的约束会被系统性淘汰,而且被淘汰的约束,后来者不知道它存在过。

**找冲突候选的范围**:只在同一个 skill、同一个 L3 键里找,不在全库里找。
Graphiti #1728 的误伤就出在候选检索不限定范围。

## 4. 证据分三档:"我能判断"的门槛

| 档 | 算这一档的 | AI 能说到哪一步 |
|---|---|---|
| `seen` 直接看到 | 当前代码 `file:line`、跑了条目自带的验证命令、读了硬件字节 —— **人照着能重做一遍** | "经验这里不对,建议改成……,证据是……" |
| `inferred` 推出来的 | 从原理推、从别处类比、从文档读 | "我怀疑这条不对,理由是……,请你判断" |
| `unseen` 看不到 | 板子不在、平台不在手边、核不清 | 只报冲突,不给结论 |

**核心规则:有实测来源的经验,只能被新的实测推翻,不能被推理推翻。**
第一性原理用来发现不对劲、提出假设;下"经验错了"这个结论,要看实际是什么。
蒸馏时专门挖这一类经验(`SKILL.md` Phase 1 镜头 D:「文档写的 X 实际是 Y」),拿原理或文档去推翻它是反的。

## 5. 冲突报告

### 格式

```
⚠ 经验冲突 C-20260928-01 · <skill> / <条目>(来源 <commit>,<日期>)
记录:C-20260928-01 · 指纹 e470f3(`decision report` 的输出原样贴在这里)
经验说:<原文一句>
现在看到:<file:line 或命令 + 输出>
我判断:stale 过期 —— <路径> 在 <commit> 改过(证据:seen)
建议:把 X 改成 Y;旧值标失效留在原处;补上适用范围
不改会怎样:<照旧经验做,下一步会怎样>
参考:同类过往记录 C-20260911-02(你当时判的是 scope)
需要你:确认改 / 不改 / 你来判断类型
```

每一项都要有。**只给结论不给证据指针的报告不算报了。**

**"记录"那一行必须先有,再有这张报告。** 它是 `decision report` 写下 AI 判断之后才打印出来的,
所以报告里有它,就说明 AI 的判断在你回答之前已经落进记录(第 7 节)。
**没有记录行的报告,当作没报**;事后发现记录里的判断和报告上写的不一样,指纹也会对不上。

### 什么时候报

- **影响下一步动作的,立刻报**,等人回复再往下走
- **不影响的,在这一步做完的汇报里一起报**,多条合成一张表
- 两种都**在改经验之前**
- 同一条经验在同一次会话里只报一次
- 报了人没回:**不改经验**;当前任务按直接看到的现状做,汇报里写明偏离了哪条经验

## 6. 确认之后怎么改

| 判为 | 改法 |
|---|---|
| `stale` / `wrong` | 按 §11 追加:旧条目划掉留原文、注明"被 C-… 替代";新条目的来源写冲突编号 + 证据指针 |
| `scope` | 在 `params/<platform>.md` 加一行变体,L2 正文不动 |
| `code-regress` | 经验不动,给它的复现记录回写一行(§7,这次是印证);代码问题单独报 |
| `clash` | 按人的决定,落选那条同 `stale` 处理 |

三条附带要求:

1. **每次改都要留下一条能跑的检查。** 用 `seen` 证据解决的冲突,当时跑的那条命令就是新条目的
   验证方式(§7)。这样每解决一次冲突,库里就多一条能直接核对的条目,
   下次同一条出问题可以直接看到,不用靠推理。
2. **这条检查必须能分辨对错:拿旧值(或故意写错的值)跑,它必须失败。** 报告里把两次运行的
   输出都贴出来,人确认改的时候连检查一起确认。
   **没有它会怎样**:检查是 AI 写的、结论也是 AI 下的,一条永远通过的检查会让任何改法都"验证通过"。
   autoresearch 能无人值守,前提是评测代码 agent 改不了(karpathy/autoresearch `program.md`:
   "The `evaluate_bpb` function in `prepare.py` is the ground truth metric");
   它的通用化版本放开了这一点,自己承认 "a user could accidentally create a verify command that's gameable"
   (uditgoenka/autoresearch `COMPARISON.md`)。
3. 每个确认过的改动单独一笔提交,提交说明里写冲突编号,撤回时 `git revert` 这一笔即可;
   改完跑 `whetstone verify`,置信度按 §7 机械表重判。

## 7. 记录格式:分两步写

**为什么分两步**:记录是 AI 写的,而 AI 正是被打分的一方。如果等人回答完再一次写一行,
AI 那一半"自己的判断"完全可以照着人的答案填,一致率就成了 100%,而且屏幕上没有任何迹象。
所以 AI 的判断**在问人之前**就要落进记录,人的回答事后追加,两行各管各的。

| 步骤 | 命令 | 写进去的 `kind` | 谁的判断 |
|---|---|---|---|
| ① 报之前 | `decision report` | `conflict-report` | AI:类型、证据档、建议、把握、理由 |
| ② 人回答后 | `decision resolve` | `conflict-resolve` | 人:决定、改成的类型、理由 |
| 漏报 | `decision miss` | `conflict-miss` | 人:这是哪一类冲突(AI 没报,所以没有 AI 那一半) |
| 考卷 | `decision exam` | `exam` | 考卷结果(第 8 节 ②) |

所有记录都追加进 `journal/review-decisions.jsonl`(格式见 `spec/review-decisions.md`)。
`conflict-report` 和 `exam` 不是决定,不进 verdict 统计。

```bash
# ① 报之前:AI 写下自己的判断,拿到编号和指纹,贴进冲突报告
whetstone decision report --entry boot-x/pitfall-7 --entry-source abc1234 \
  --ai-type stale --ai-evidence seen --ai-action update --ai-certainty high \
  --subject "OTP[ADDR] 的读法" --reason "路径在 def5678 改过" --source def5678 --safety --blocking
#   → reported C-20260928-01 · fingerprint e470f3
# ② 人回答后:追加人的决定
whetstone decision resolve --conflict-id C-20260928-01 --verdict amend --final-type scope \
  --reason "不是过期,是 SoC-Y 上寄存器布局不同"
# 漏报:人发现的,AI 用过却没报 —— 这个命令根本没有 --ai-* 参数
whetstone decision miss --entry boot-x/pitfall-3 --final-type wrong --verdict accept \
  --subject "…" --reason "你发现的" --source <会话>
# 考卷每考一次记一行
whetstone decision exam --result pass --reason "考卷 v1,8 题全对,模型 X"
```

### 两步之间靠什么连上、靠什么防改

| 规则 | 挡住的是 |
|---|---|
| `report` 自动编号 `C-YYYYMMDD-NN`,**同一编号不能报第二次** | 判断写下之后再改写 |
| `report` 存下时间和**指纹**(对 AI 判断各字段取 SHA-256 的前 6 位);每次读取都重算,对不上的那条不计分并报出来 | 在文件里直接改旧行(§11 只追加) |
| `resolve` 找不到对应的 `report` 就拒收;手写进文件的、排在报告前面的回答不算 | 先有答案后补判断 |
| 同一条经验在同一个 source 里报了多次:**只给第一次的判断打分**,对的是这几次里**最新的回答**,并报出"报了不止一次" | 看到回答后换个编号重报一次 |
| 没有 `add --kind conflict` 这条一行写两边的路,用了直接拒收并指向 `report` | 绕开两步 |

`resolve` 里"类型没改"指的是**它所回答的那次报告**的类型;和第一次报告的类型比,才是打分用的判对与否。

`verdict` 在 `resolve` 和 `miss` 里的意思:

| verdict | 意思 |
|---|---|
| `accept` | 按 AI 判的类型和建议处理了 |
| `amend` | 处理了,但类型或改法被人改了 |
| `reject` | 不改:人判断其实没冲突,或维持经验 |
| `defer` | 要补测一次才能定;之后再 `resolve` 一次,最新的回答算数 |

拒收规则(拒收时一行都不写):`resolve --verdict accept` 却改了类型(那是 `amend`);
`--final-type none` 配的不是 `reject`;`miss` 的类型写成 `none`(没冲突就不是漏报)。

字段:

| 字段 | 在哪一步 | 内容 |
|---|---|---|
| `conflict_id` | ① ② | `C-YYYYMMDD-NN`,提交说明引用它 |
| `reported_at` / `resolved_at` | ① / ② | 精确到秒的写入时间,工具自动填,不接受手填 |
| `fingerprint` | ① | 见上表 |
| `entry` | ① 漏报 | `<skill>/<条目标识>` |
| `entry_source` | ① | 经验自己的来源 commit;没有就不写这个键 |
| `ai_type` | ① | `stale` / `scope` / `wrong` / `code-regress` / `clash` |
| `ai_evidence` | ① | `seen` / `inferred` / `unseen` |
| `ai_action` | ① | `update` / `variant` / `supersede` / `keep` / `ask` |
| `ai_certainty` | ① | `high` / `med` / `low` —— AI 对**自己这次判断**有几成把握,不是经验的置信度 |
| `ai_reason` | ① | AI 为什么这么判 |
| `final_type` | ② 漏报 | 人改成的类型;`none` = 其实没冲突(误报)。和 AI 的一样就不写 |
| `blocking` / `safety` | ① | 是否卡住了下一步 / 是否涉及安全相关经验(第 9 节) |
| `source` | ① 漏报 | 本次会话 / commit 指针。**同一条经验在同一个 source 里只算一条** |

**人零额外动作**:人回复的"改 / 不改 / 是 scope"就是决定,两步都由 AI 执行。
**还没回答的报告不计分**,`stats` 会把它们列成"等你回答"。

## 8. 打分

按第一次报告的 **`ai_type` × `ai_evidence`** 分组算四个数。"已判"= 有回答、回答不是 `defer`、
人的类型不是 `none`;还在等回答的不算。

| 指标 | 算法 | 为什么要它 |
|---|---|---|
| 类型判对率 | 人的最终类型等于 AI 第一次判的类型的条数 ÷ 该组已判条数 | 决定这一组能不能简化确认 |
| 漏报 | `conflict-miss` 的条数,按人给的类型归组 | 最危险的失败,不会自己暴露 |
| 误报率 | 人判为 `none` 的条数 ÷ 该组报告数 | 太多人就不看了,后面的数据全废 |
| 校准 | 按 `ai_certainty` 分组的判对率 | `high` 组不明显高于 `low` 组,说明 AI 的把握不可信,就不拿它当依据 |

**判对率用精确二项下界,不用点估计。** 点估计会高估:Trust or Escalate(arXiv 2407.18370)
里直接用样本一致率定阈值,达标率只有 47.5%(Tab.2)。单侧 Clopper-Pearson 下界,δ=0.1:

| 样本 | 能保证的判对率下限 |
|---|---|
| 10 条全对 | 79.4% |
| 20 条错 2 条 | 75.5% |
| 22 条全对 | 90.1% |
| 45 条全对 | 95.0% |

**不单看"被采纳率"。** 只看它,AI 会学会只报稳的、难的不报,分数越来越高、漏报越来越多。
所以**漏报比误报罚得重**:误报只拉低判对率;漏报直接让该组退回完整确认(第 9 节)。

### 两道防止"看起来在进化、其实在空转"的检查

**自进化的循环很容易只在纸面上跑。** darwin-skill 自己的记录里,早期 40 次优化 0 次回滚、
67% 是没真跑的推演(`references/skilllens-evidence.md`);sky-skills 的 design-evolve
设计完整,ledger 里一次真实改动都没有。下面两道检查就是防这个的:

**① 推断占比。** `stats` 同时报出 `inferred` + `unseen` 占全部冲突的比例。
超过 30% 就在输出顶部警告:这批分数大多建立在 AI 的推测上,不能拿来放宽确认。
(照搬 darwin-skill `SKILL.md`:"dry_run 比例 > 30% → 评估失效警告";30% 同样是拍的。)

**② 考卷。** 一小套**答案已知**的冲突样例,每个类型至少一题,外加两类专门的陷阱题:

- **`code-regress` 陷阱**:代码改成了经验警告过的写法,正确答案是"不改经验、报代码" ——
  考的是 AI 会不会拿原理去"纠正"一条坑
- **核不清题**:证据不足,正确答案是 `unseen` / `ask` —— 考的是 AI 该说"不知道"时会不会说。
  照搬 nuwa-skill 的边缘测试(`SKILL.md` 4.2 节):"期望结果:可能...但不确定;不应该斩钉截铁"

用法:第一次用 AI 判冲突前考一次,之后每改一次第 3 节判定规则或换模型再考一次,
每次用 `whetstone decision exam` 记下结果。**没有考卷记录,`stats` 不放宽任何组**;
"改了规则或换了模型要重考"这一条,工具判断不了,只能靠人记着。
**有一题答错,所有组退回完整确认。** 这和 darwin-skill 的劣化对照(故意造 4 类劣化版本,
5 个盲评裁判必须全部识别出来)、本仓 `bin/verify_mutation_test.sh`(故意改坏,自检必须报红)是同一个思路:
先证明判官分得出对错,再用它的判断。

## 9. 分数用来做什么

**模型本身不会变。** "越来越聪明"落在三样会增长的东西上:

**① 过往记录当参考**:判新冲突前,先找同 skill、同 `ai_type` 的过往记录,报告里注明参考了哪几条
(Trust or Escalate 的置信度就是这么来的:拿历史人工判断当示例,看几组示例下判断是否一致)。

**② 反复被改的判断变成规则提案**:同一种"AI 判 X、人改成 Y"攒够 `SIGNAL_MIN` 个不同来源,
`stats` 点名,AI 提议改第 3 节的判定规则。提案按 `kind: framework` 记,同样要人确认。

**③ 确认方式分档** —— **分数只改"怎么问",不改"问不问"**:

| 档 | 怎么问 | 进这一档的条件 |
|---|---|---|
| 完整确认 | 报告全文,逐条确认 | 默认,所有组从这里起步 |
| 摘要确认 | 一行摘要,证据可展开,仍逐条确认 | 仅 `seen` 组;判对率下界 ≥ 90%(最少 22 条、全部判对) |
| 批量确认 | 任务结束时一次列出,逐条勾选 | 仅 `seen` 组;下界 ≥ 95%(最少 45 条、全部判对) |

- 任何档位都**不会自动改经验**
- 该组出现一次漏报 → 立刻退回完整确认,之后只按漏报之后的记录重新算
- `inferred` / `unseen` 组永远完整确认:AI 没看到实际情况,它判对的次数说明不了什么
- `safety=true` 的永远完整确认,并且改之前重测一次

**经验条目自己的分**:用了没出问题 → 复现记录回写(§7);
同一条经验在 2 个不同来源里被判为冲突 → 标"待复核",下次蒸馏比对已有库时优先看。

**门槛数(90% / 95% / δ=0.1 / 2 个来源)都是拍的。** 按框架自己的尺子它们属于 L3,
由记录攒起来之后校准,别为它们辩护。

**可选:盲判抽样。** 人先看到 AI 的结论,判断会被带偏,一致率虚高
(arXiv 2603.11821:病理专家看到 AI 建议后,7% 放弃了原本正确的判断)。
缓解办法是某些报告只给证据、先请人判类型,再亮出 AI 的判断。代价是多问一次。
建议**只在某一组快到摘要确认门槛时打开**:那时这组数据马上要被拿来放宽确认,虚高最有害。

## 10. 禁止清单

| # | 绝不做 | 为什么 |
|---|---|---|
| 1 | 没经人确认就改经验(任何档位) | 这是本规范的前提;档位只简化问法 |
| 2 | 用推理推翻有实测来源的经验 | 经验常记的就是"推理 / 文档说 X、测出来是 Y"(`SKILL.md` Phase 1 镜头 D) |
| 3 | 删除旧条目 | 只标失效留原文(§11);删了,后来者不知道它存在过 |
| 4 | 发现对不上,自己绕过去不报 | 最常见、最难发现的失败 |
| 5 | 报告只给结论,不给证据指针 | 人没法核,只能盲信或重查 |
| 6 | 对 `safety=true` 的经验简化确认或跳过重测 | 错了往往不可逆 |
| 7 | 只按被采纳率给 AI 打分 | 会奖励少报 |
| 8 | 在全库范围找冲突候选 | 误伤(Graphiti #1728) |
| 9 | 把"补充"当"矛盾"处理 | 删旧加新会把经验打碎(Memory-R1) |
| 10 | AI 改打分规则:第 3 节判定表、第 8 节算法、统计代码、考卷 | 被打分的一方能改尺子,分数就没有意义(autoresearch 的评测代码只读);只能按 `kind: framework` 提议,人确认 |
| 11 | 用"某些关键词出现了几次"当质量检查 | 查的是字在不在,不是对不对(nuwa-skill 的 `quality_check.py` 出现 2 次「矛盾 / 张力」就算过) |
| 12 | 先问人,再记自己的判断;或听完回答换个编号重报一次 | 被打分的一方照着答案填自己的判断,一致率虚高且看不出来(第 7 节) |

## 11. 边界

- **不能强制上报。** 规则只能要求 agent 报;漏报只能靠人发现时说一句,再由 AI 补记。
  漏报的真实数量永远只多不少。
- **只有一个审核人。** 算不出人与人之间的一致基线(Alt-test,arXiv 2501.10970,要 ≥3 人),
  "AI 判得和人一样"不等于"判对了"。
- **两点核对只适用于有来源 commit、说法能在代码里查到的经验。** 板上状态类要重测;
  拿不到板子就是 `unseen`。
- **两步记录挡得住"事后改",挡不住"事后才写"。** AI 若等人回答完才跑 `report`,
  文件里的顺序照样是先报告后回答。能戳穿它的只有报告里那行"记录:编号 · 指纹" ——
  没有这一行的报告当作没报;有这一行,说明判断在你回答前已经写下。这一关最终靠人看一眼。
- **只覆盖用的时候撞上的问题。** 没被用到的经验不会被核;"装上这个包使用者是否变强"
  (§14 末)仍然没有完整的测法,本规范只补上"用时发现不对"这一部分。
