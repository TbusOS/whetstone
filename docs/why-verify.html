I marked 61 entries “high confidence.”
Not one could name a test. 我给 61 条经验标了「高置信度」
没有一条说得出验证方式

I keep a skill library — markdown files my coding agent loads when a task matches. Secure boot, SDK migration, partition layouts. Real work, distilled after the fact so the next project starts where the last one ended. 我维护一个 skill 库 —— 一堆 markdown，任务匹配上了编程 agent 就加载。安全启动、SDK 升级、分区布局。都是真干过的活，事后蒸馏下来，好让下个项目从上个项目结束的地方开始。

Months ago I wrote the rule that governs it, in my own framework document, in bold: 几个月前我在自己的框架文档里写下了管这件事的规矩，加粗的：

No entry may be marked high confidence without an executable check that actually passed. 没有一条实测通过的可执行检查，不许标 high。

Last week I finally wrote the checker. I pointed it at the two packages that framework had produced. 上周我终于把检查脚本写了出来。拿它对准这套框架自己产出的两个包。

61entries marked high条标着 high
0could point to a passing test条能指出实测通过
54graded above what the table allows条置信度越权上调
180errors across two files I shipped个错，在两个我已上线的文件里

The rule was never broken by anyone. It was just never enforced by anything. 规矩没有被任何人违反。它只是从来没有被任何东西执行过。

Prose rules rot散文写的规矩会烂掉

Here is the failure mode, and I don’t think it is specific to me. You write a discipline into a document. The model reads it at the top of a session and follows it. Forty messages later the document has been summarised, the context has turned over, and the model is producing entries that look exactly like the compliant ones — same fields, same shape, same confident label — because the shape is what survived and the reason did not. 失效的过程是这样的，我不认为只有我会踩。你把一条纪律写进文档。模型在会话开头读到它，照做。四十条消息之后，文档被摘要压缩了，上下文已经换了一轮，模型继续产出的条目看起来跟合规的一模一样 —— 字段一样、形状一样、标签一样自信 —— 因为活下来的是形状，死掉的是理由。

Nobody notices, because the failure is silent. A wrong high does not crash. It sits there looking authoritative until, six months later, someone acts on advice that was true once, on one board, and is now quietly false. 没人发现，因为这种失效是无声的。一个标错的 high 不会崩。它就那么摆着，一副权威样子，直到半年后有人照着一条「曾经在某一块板上成立、现在已经悄悄不成立」的建议动手。

A rule that only a model enforces is one context window away from not existing. 一条只靠模型自觉遵守的规矩，离「不存在」只差一个上下文窗口。

So the decidable part became a command所以我把机械可判的那部分做成了命令

Not all of it. Some of the discipline genuinely needs judgement — is this principle really exception-free?, was that contradiction preserved or averaged away? Mechanising a judgement that is not mechanical only manufactures false positives, and a checker that cries wolf gets muted, which is worse than no checker. 不是全部。有些纪律真的需要判断力 —— 这条原理是不是真的举不出反例？、那个矛盾是被保留了还是被和成了平均值？ 把本来不机械的判断硬做成机械的，只会制造假阳性；而一个总在狼来了的检查器会被静音，那比没有检查器更糟。

But a lot of it is just decidable:但相当一部分，就是可判的：

  • Does this entry carry a source, a date, a reproduction record, a verification method, a confidence level?这条带没带来源、日期、复现记录、验证方式、置信度？
  • Is the date absolute, or does it say “recently”?日期是绝对日期，还是写着「最近」？
  • Does the declared confidence exceed what the table allows, given the evidence actually present?按现有证据，标的置信度有没有超过表允许的上限？
  • Is the reproduction record a list of platforms, or someone typing “3 times”?复现记录是一张平台列表，还是有人打了个「3 次」？
  • Was this pitfall split into a transferable lesson and a platform fact, or is the lesson welded to the one chip where you learned it?这条坑拆成「可迁移的教训 + 平台专属的事实」了吗，还是教训被焊死在你学到它的那一颗芯片上？

Thirty-seven checks. It reports, and exits non-zero:37 条检查。报错，退出码非零：

$ whetstone verify examples/demo-skill --brief

ERROR (5)
  ✗ SKILL.md:31        [V16] 复现记录 has two lines for the same platform
  ✗ SKILL.md:31        [V12] L2 claims 置信度 high, the table allows only low
  ✗ pitfalls.md:5      [V14] 复现记录 is a bare count 「2 次」
  ✗ params/soc-x.md:6  [V10] L3 claims high — 验证方式 never passed a test

summary: 5 error(s), 2 warning(s), 0 info

Trimmed for width; the real lines also carry the entry name. examples/demo-skill ships in the repo, deliberately flawed — run it and see the untrimmed version. 为宽度做了截短，真实的行还带条目名。examples/demo-skill 就在仓库里，故意写坏的 —— 跑一遍就能看到未截短的版本。

The one design decision I would defend hardest: a reviewer may downgrade any entry, and may never upgrade past the conditions. Above the cap is an error; below it is only a note. Because the failure mode is not people being too harsh on their own notes. 最想为之辩护的一个设计决定：人审可以把任何一条下调，永远不能越过条件上调。 高过上限报错，低于上限只是提示。因为真正会发生的失效，从来不是人对自己的笔记太苛刻。

Then three reviewers took it apart然后三个评审把它拆了

I asked three independent reviews to attack it, in separate contexts so none inherited my assumptions. The third came back “blocking” and listed four ways to get a single-platform lesson graded high with zero warnings. 我请了三份独立评审来攻击它，各自在独立的上下文里跑，谁也不继承我的预设。第三份回来判定阻塞，列出四条能让「单平台的经验」在零告警下拿到 high 的路。

  1. Delete one separator删掉一个分隔符

    Reproduction lines are platform · date · pointer, keyed by platform. Drop the · and the whole line becomes the key — so two entries for the same board read as two different platforms. The gate that exists to stop one project counting twice was defeated by removing a dot.复现记录的格式是 平台 · 日期 · 指针，按平台做唯一键。把 · 去掉，整行就成了键 —— 于是同一块板的两条记录读成了两个不同的平台。那道专门防止「同一个项目算两次」的关口，被删掉一个点破掉了。

  2. Mention “L3” in a heading在标题里提一句「L3」

    Layer was inferred from the nearest heading containing L1–L4. A section titled “Don’t put L3 values in the body” — an instruction against the thing — reclassified everything under it and raised the cap.层级是从最近的、含 L1–L4 的标题推断的。一个叫「不要把 L3 的值写进正文」的小节 —— 一句反对这件事的告诫 —— 把它底下所有条目重新分了类，还把置信度上限抬高了一档。

  3. Add a suffix加个后缀

    soc-x and soc-x(second run) normalised to different keys. Same platform, two lines, gate cleared.soc-x 和 soc-x(第二次) 归一化出两个不同的键。同一个平台，两行，关口通过。

  4. Omit the leading pipe不写前导竖线

    GFM tables do not require | at line start. Mine did. A whole platform-parameter file could be invisible to every check while reporting zero problems — including the check whose entire job was to notice that a table had no confidence column. The hole and its patch used the same broken ruler.GFM 表格不要求行首有 |，我的解析器要求。于是一整份平台参数文件可以对所有检查隐形，同时报告零问题 —— 包括那条专门用来发现「这张表没有置信度列」的检查。补漏的和被补的洞，用的是同一把坏掉的尺子。

All four are fixed, and each is now a mutation-test entry: delete the fix, the suite must fail. 四条全修了，而且每一条现在都是一个变异测试：把修法删掉，整套测试必须报错。

The part I would rather not write不太想写的那部分

While making the tests prove the fixes, I found two of my own tests were fake. One watched the wrong error code — it passed because a different rule fired. The other declared high in its own fixture data, so it errored whether or not the bug was present; it proved nothing, and had been green the whole time. 在给这些修法补测试的时候，我发现自己写的两条测试是假的。一条盯的是错误的检查码 —— 它能通过，是因为另一条规则响了。另一条在测试数据里就写了 high，于是不管 bug 在不在都会报错；它什么都没证明，而且一直是通过的。

And the coverage check I had added to catch exactly this? Its failures ran inside a pipeline, so the counter incremented in a subshell and vanished. It printed FAIL and reported 0 failed. 那我为了抓这种事专门加的覆盖率检查呢？它的失败跑在管道里，计数在子 shell 里加，加完就没了。它打印 FAIL，然后报告 0 failed。

A test that passes is not the same as a test that would fail. The only way to tell them apart is to break the thing on purpose and watch. 「测试通过了」和「这条测试真的测住了」是两回事。区分它们的唯一办法，是故意把东西弄坏，然后看。

Which is the same lesson as the 61 entries, one level up. I had written the rule. I had written the test. Neither was doing anything. 这跟那 61 条是同一个教训，只是高了一层。规矩我写了。测试我也写了。两个都没在干活。

The transferable part能带走的那部分

If you keep any kind of agent memory — a skill library, a rules file, a CLAUDE.md, a corpus you curate by hand — the question worth asking is not what does it contain. It is: 如果你也维护任何形式的 agent 记忆 —— skill 库、规则文件、CLAUDE.md、手工整理的语料 —— 值得问的不是里面有什么，而是：

Which of my rules would still be true if I stopped believing in them? 我这些规矩里，哪几条在我不再相信它们之后还成立？

For every discipline you have written down, one of three things is true: a command enforces it, a person checks it on a schedule, or it is decoration. There is no fourth category, and decoration is the default. 对每一条你写下来的纪律，三件事里必有其一：有命令在执行它、有人按周期检查它、或者它是装饰。没有第四种，而且装饰是默认值。

The tool is whetstone — MIT, standard library only, works with any runtime that reads the Agent Skills layout. It ships a deliberately broken example package so verify has something to catch, and --explain prints not just what it checks but where each check is narrower than the rule it serves, and what it refuses to judge at all. 工具是 whetstone —— MIT，只用标准库，任何读 Agent Skills 布局的 runtime 都能装。它自带一个故意写坏的示例包，好让 verify 有东西可抓；--explain 不只打印它查什么，还打印每条检查比它服务的规则窄在哪、以及它压根不判什么。

I would rather it be honest about its blind spots than pretend it has none. That was the whole problem in the first place. 我宁愿它诚实地说出自己的盲区，也不要它假装没有。当初的问题就出在这儿。
