Sort persistent instructions by "does every turn need this?". The global CLAUDE.md loads in full every turn — pile too much in and you burn tokens, lower adherence, and (when it is dense with dual-use terms) trip server-side safety classifiers. Keep only neutral, always-needed rules there; push the rest to on-demand skills. 把持久指令按「是否每轮都需要」分层。全局 CLAUDE.md 每轮全文载入 —— 堆太多就吃 token、降遵循度，内容密度高时还容易触发服务端安全分类器误报。那里只留中性、每轮都要的规则；其余推给按需 skill。

Iron rule:铁律： an always-on behavioral constraint must not become an on-demand skill. A skill needs a trigger; a rule like "never add a certain signature" or "output style" must apply every turn and has no trigger — as a skill it would silently fail to load most turns. 常驻行为约束不能做成 on-demand skill。skill 要触发词才载入；像「禁某类署名」「输出风格」这种每轮都要生效、又没有触发场景的规则，做成 skill 大多数轮次不触发 = 静默失效。

Watch out注意

Four things that bite四个坑

  1. @import loads in full at launch — it does not save context. Its value is single-source + organization, not fewer tokens. What actually stays out of context until needed is an on-demand skill — so keep heavy content in skills, not imports.@import 启动时全量载入，不省 context。它的价值是单一真相 + 组织，不是省 token。真正「不触发不载入」的是按需 skill —— 所以重内容留 skill，别 @import。
  2. Keep the always-on layer neutral and low-density. That is what controls false positives — not any trick to route around a classifier.常驻层保持中性、低密度。这才是控制误报的办法，不是靠什么技巧绕过分类器。
  3. If the data repo carries real values (internal paths, org names, platform params), make it private. The tool repo stays generic and public.数据仓若含真实值（内部路径 / 组织名 / 平台参数），设 private。工具仓保持通用、可公开。
  4. Multi-root project (code and notes on different mounts): put a CLAUDE.md at each root; the thin one just @imports the main hub.多根项目（代码和笔记在不同挂载点）：每个根放一个 CLAUDE.md，薄的那个只 @import 主 hub。
