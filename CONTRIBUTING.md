# Contributing

Thanks for looking. This project is small and opinionated, so this file is mostly about
which changes fit and which do not — that tends to save more time than a style guide.

## The one rule this repo holds itself to

Every mechanically decidable rule must be a check that runs. If you add a rule to
`references/extraction-framework.md` or `spec/skill-package.md` and it can be decided by
reading the file, it belongs in `bin/verify.py` too. A rule that only a reader enforces
is one context window away from not existing — that is the entire premise of the project,
and it applies to the project itself.

Corollary: **a fix without a test that would fail without it is not a fix.**

```bash
bash bin/verify_selftest.sh          # 120 assertions, both directions, coverage-enforced
bash bin/verify_mutation_test.sh     # deletes each check in turn; the suite must fail
bash adapters/capture/selftest.sh
bash autoupdate/selftest.sh
```

All four must pass before a change is proposed. The mutation battery is the one that
matters most: it is how the two fake tests in this repo's own history were found.

## Adding a check to `verify`

1. Implement it in `bin/verify.py` with a new `Vxx` code.
2. Publish it in the `--explain` text, including where it is **narrower** than the rule
   it serves. Overstating coverage is worse than a gap, because people stop looking.
3. Add both directions to `bin/verify_selftest.sh`: a fixture that makes it fire, and a
   fixture that keeps it quiet. The coverage block at the end of the selftest fails the
   run if either is missing, so this is not optional.
4. Add a mutation entry to `bin/verify_mutation_test.sh` that removes your logic and
   proves the suite goes red.
5. Make the fixture *discriminating*. Ask: if I deleted the logic, would this assertion
   still pass for some unrelated reason? Two assertions in this repo did exactly that.

If a rule needs judgement — whether a principle is really exception-free, whether a
contradiction was preserved — **do not mechanise it**. Add it to the "deliberately not
decided" list in `--explain` instead. A checker that cries wolf gets muted, which is
worse than no checker.

## Changing the framework

`references/extraction-framework.md` is the core. Changes there ripple into `SKILL.md`,
`spec/skill-package.md`, the templates, and `verify`. If you change a rule, say in the PR
which of those you updated and which you deliberately did not.

## The pages under `docs/`

They are generated by hand and must pass the design gates before merge:

```bash
~/.claude/skills/design-review/dr-cli docs/<page>.html
```

Bilingual EN/zh copy is expected; Chinese text uses full-width punctuation (half-width
commas next to Han glyphs break CJK metrics).

## What does not fit

- Runtime-specific behaviour outside `adapters/`. The output is plain markdown and must
  load in anything that reads the Agent Skills layout.
- Required dependencies. `bash` plus the Python standard library, and nothing else.
- Real platform values in this repo. Distilled packages carry real addresses and vendor
  names; those stay in your own library. Anything here is generic (`soc-x`, `proj-a`).

## Reporting something

Issues are welcome, including "your check fired on my perfectly good package" — false
positives are treated as bugs of equal weight to missed violations. Please include the
smallest package that reproduces it, and the output of `whetstone verify <pkg> --json`.

## Commits

Conventional prefixes (`feat:` `fix:` `docs:` `chore:` `test:`). Say what changed and
why; if a reviewer found the problem, say so — the history of this repo is more useful
as a record of what was wrong than as a record of what was added.
